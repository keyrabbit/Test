Risks

#1 The character is the product critical · mitigated

A focus timer is a commodity; the reason someone keeps this on screen is that they like the creature. The reference sheet has now been approved and traced into the shipping geometry, so the biggest unknown is closed. What remains open is judgement, not delivery: whether the character actually charms real people (g3-charm-test) cannot be self-assessed, and every downstream asset (poses, decorations, app icon, Steam capsules) is still to be produced from the sheet.

Mitigation. Prompt A issued to the owner on day one as issue #2, approved, and traced from measurements rather than eyeballed (art/PROVENANCE.md, DECISIONS.md D18). The art was wired to the full animation rig through art/manifest.json from the start, so the placeholder-to-final swap touched art only, not behaviour. Prompts B-E are now unblocked.

https://github.com/keyrabbit/Pet/issues/2

#2 Dashboard cannot auto-publish low · mitigated

DASHBOARD_PUSH_TOKEN does not exist, so CI cannot push to keyrabbit/Test.

Mitigation. Dashboard published to docs/dashboard/ in this repo and mirrored by hand to Test/pet/. See DECISIONS.md D8.

#3 MSIX build on a hosted runner is unverified medium · closed

Packaging for the Store needs Windows SDK tooling (MakeAppx) that had not been exercised on a GitHub-hosted runner. Discovering a gap here late would have blocked submission.

Mitigation. Closed: both packaging targets build on windows-latest, verified by CI run 30564197213. The remaining packaging blocker is the shipping signature, which needs a Partner Center identity and is a G6 item, not a tooling risk.

https://github.com/keyrabbit/Pet/actions/runs/30564197213

#4 Only 200% scaling is testable on the dev host medium · mitigated

The development display is fixed at 2880x1920 @ 200%, and Windows Sandbox turned out not to be the second DPI surface this risk assumed: hyperloop display --action set-dpi writes the registry and then needs a sign-out, which Sandbox cannot perform, and provisioning a Hyper-V VM instead fails on this host with 'Setting up VMs requires admin'. There is also only one virtual display, so multi-monitor DPI cannot be reproduced at all.

Mitigation. The DIP-to-pixel placement calculation was extracted into a pure function, TaskbarGeometry.PlaceCompanion, and pinned by 16 unit tests at 100/125/150/175/200% across all four taskbar edges and a mixed-DPI two-monitor arrangement, so the matrix runs on every push. 200% is additionally verified live with a 0,0 size and position delta. Residual exposure: the calculation reaching the screen intact is confirmed at 200% only.

#5 Two section 8 performance budgets are missed medium · open

Release working set is 104.5 MB against an 80 MB budget, and the self-contained folder is 178 MB against 120 MB. Neither is a leak or a regression: the working set is flat over time and only 22.2 MB of it is private, the rest being shared framework image pages, and the folder size is dominated by WPF and the runtime, which cannot be trimmed. Both measurements were taken on a machine with WPF render tier 0 (software rendering, no GPU), which inflates WPF working set by an unknown margin.

Mitigation. Measured rather than estimated, and recorded as missed rather than rounded away (docs/performance.md). The obvious fix - single-file with compression - was tried and rejected on measurement: it halves the download but takes working set to 222 MB and private memory to 98 MB, and adds ~240 ms to startup (DECISIONS.md D21). Closing this honestly needs a re-measurement on hardware with a real GPU; a real reduction needs a UI framework that supports trimming, which is not a G5 change.
